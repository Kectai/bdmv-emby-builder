# 隐私与安全边界

本文说明 BDMV → Emby Builder 处理哪些本地数据、哪些文件不应公开，以及执行阶段的写入边界。具体使用命令和配置字段以 [README](../README.md) 为准。

## 数据与网络

项目不请求网络服务，也不上传媒体、元数据或路径。扫描、规划和构建只使用：

- 用户指定的 BDMV、META、MPLS 和 M2TS；
- 本机 FFmpeg/FFprobe 输出；
- 用户提供的 TOML；
- 项目生成的 JSON 计划、结果和目标库状态。

离线运行不等于生成物适合公开。以下内容通常包含绝对路径、卷名、媒体发行目录、片名或完整库清单：

- 本地任务 TOML；
- `scan.json`、`plan.json` 和 `*-results.json`；
- 目标库中的 `.bdmv-emby-state.json`；
- 终端输出、错误栈和手工采集的 FFmpeg/FFprobe 日志。

公开 Issue、日志或示例前，应把路径替换为 `/path/to/BDMV_LIBRARY`、`/path/to/EmbyLibrary` 等占位值，并确认目录名、标题和工具路径不会暴露不希望公开的媒体清单或用户名。仓库不跟踪从真实媒体库导出的 plan、results、state、ffconcat 或逐盘映射表；需要回归特定行为时，应优先在测试中构造不含真实作品名称的最小数据。根目录 `.gitignore` 排除常见本地任务和全库结果，但不能替代提交前检查。

建议在提交前运行：

```bash
git diff --cached
git grep -n "/Users\|/Volumes\|[A-Za-z]:\\\\Users" -- ':!docs/privacy-and-safety.md'
```

第二条命令只是辅助检查，不能覆盖所有自定义挂载点、UNC 路径或敏感目录名。

从工作树删除敏感文件不会清除既有 Git 历史。首次公开仓库前，应从干净历史发布，或使用经过复核的历史重写流程清除旧任务配置和全库快照；历史重写不由本工具自动执行。

## 文件系统边界

- `scan` 和 `plan` 不创建媒体文件；
- `build` 仅在显式使用 `--execute` 时写入目标目录；
- 源 BDMV 只读打开，不执行移动、重命名或删除；
- 计划和执行都校验源、目标及每个文件的解析后路径，防止越出声明根目录；
- 审计 JSON 必须使用 `.json` 文件名，并会先排除源目录、整个目标媒体库、输入配置/计划、媒体成品和内部控制路径；失败处理也不会向已判定危险的结果路径写入；
- 路径边界把大小写差异和 Unicode 规范化差异保守地视作同一路径，避免同一计划跨 APFS、NTFS 和大小写敏感文件系统时改变安全含义；
- 扫描、规划和执行会校验 BDMV、PLAYLIST、STREAM、MPLS、M2TS 与 META 的标准结构关系；执行计划必须显式携带真实 BDMV 路径，MPLS 必须直属其 `PLAYLIST`，源片段必须是其 `STREAM` 下的规范五位编号 M2TS；执行前还会重新解析 MPLS，并逐项绑定 clip、顺序、in/out、分段起点和总时长，不再从计划字段猜测 libbluray 内容或根目录；为避免嵌套链接和 libbluray 隐式读取改变边界或阻塞，BDMV 树内不接受符号链接、Windows junction、reparse point、FIFO、socket 或设备文件；MPLS 与 META 采用有大小上限的普通文件读取；
- 媒体输出必须是目标根下的规范相对文件路径，不能等于目标根，也不能进入 `.bdmv-emby-state.json`、`.bdmv-emby-build.lock` 或 `.bdmv-emby-work`；
- 媒体路径分段同时遵守 Windows 尾随点/空格、设备名、控制字符和长度限制，避免计划跨平台后指向不同文件；工作控制文件通过同目录临时文件原子替换，不跟随预置的叶子符号链接或硬链接；
- 目标目录不能位于源目录内；即使目标根是源目录的父目录，具体输出也不能进入源 BDMV；
- `task.source` 不接受直接指向 `BDMV` 本身；必须选择其盘根或更上层目录，避免 libbluray 为读取盘根而越出声明源边界；
- 现有目标默认只校验，不覆盖；`--overwrite` 仅替换已通过边界检查的同名目标；
- 临时媒体写入目标输出目录中的随机隐藏文件，校验成功后原子替换；
- 工具新建的 POSIX 媒体目录使用 `0755`，copy/remux 成品使用 `0644`；已有目录和 hardlink 源文件权限不被修改；
- 同一目标根目录在整个构建期间持有操作系统级独占锁（POSIX `flock` / Windows byte-range lock），避免两个执行进程同时写入；`.bdmv-emby-build.lock` 是只含固定标识、不记录主机名、PID 或路径的常驻锚点，是否占用由 OS lock 决定，不根据文件存在或旧 PID 猜测，也不删除“陈旧锁”。
- 已有媒体成品和 `.bdmv-emby-work` 不接受符号链接、junction 或 reparse point，`--overwrite` 也不会保留链接型媒体叶子；状态重定位扫描不会跨越链接型目录，也不会把状态中记录的原盘源路径当作成品，避免身份误报、越界读取或把工作文件写到目标根之外。
- state 只读取有大小上限、链接计数为 1 的普通非链接文件；lock 锚点同样必须是链接计数为 1 的普通非链接文件，但占用判断只依赖当前进程持有的 OS lock，不信任旧 JSON/PID。两者都不接受符号链接、硬链接、junction、reparse point 或 FIFO，避免控制路径指向其他文件身份。

## 硬链接边界

硬链接与源 M2TS 指向同一文件内容，不是副本：

- 删除其中一个目录项不会删除另一个目录项；
- 对任一链接执行原地内容写入，会影响所有链接；
- `hardlink_only` 只有整张盘的任务都满足一对一完整文件和链接能力时才执行；
- `hardlink_remux` 在完整单段无法链接时降级为复制，需要组合或裁切的内容仍生成独立重封装文件。

如果后续程序可能原地修改媒体文件，使用 `copy_remux`，或先确认该程序采用“新文件写入后替换目录项”的安全行为。

## 删除、恢复与备份

项目不会自动删除旧计划产生但新计划不再引用的媒体或状态记录。重规划后，应先比较新旧计划，再人工处理旧派生内容。不要用源 BDMV 目录作为清理目标。

Emby 派生目录可根据保留的 BDMV 和计划重新生成，但同盘硬链接不能抵御硬盘损坏。独立备份应位于另一存储介质，并经过恢复验证。

## 报告问题

报告问题时优先提供最小化、匿名化资料：项目版本、操作系统、Python/FFmpeg 版本、相关 playlist 的结构摘要、错误信息和去除绝对路径后的单个 job。不要上传原始媒体、完整库计划或包含个人路径的状态文件。
